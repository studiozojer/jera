# Retire posted drafts when a writing session opens

David reported posted text reappearing in the next new-post composer. His requested lifecycle retains the draft cache after publication and clears it only when opening the next writing context, after confirming that its posting intent exists. Unsent or uncertain text remains recoverable. The publication lookup currently uses Snapback `postForIntent`; a future indexer can supply the evidence through the existing Request boundary.

## Reproduction and mechanism

At `42ea4fa`, the normal macOS Chromium reproduction posts a 65-character synthetic draft, opens New post and finds the same 65 characters both immediately and 1.2 seconds later. No development error overlay is present. Durable adapter tests show that the old publish path clears its journal record, so this is not proof of a failed disk clear.

The authored `afterPost` cleared `editorContext`, rearming a hydration task even outside the composer. That task copied `savedDraft` into editor state while the resource’s refresh was still in flight. Exact deliberately retains the last resource answer during refresh; later answers did not reinitialize an editor whose context was already marked current. The SDK documentation explains kept/retained answers in `docs/contract-for-agents.md` under child form initialization and data requests. In the pinned Rust runner, `runner/src/runner/commit.rs` mutation settlement calls `force_refresh` and proceeds to settlement; this is a scheduled re-read, not a guarantee that a subsequent action sees its completed answer. Native hosts can also seed file-backed resources from kept answers across launch. The browser reproduction establishes the app race; it is not a separate native trace or proof of an engine defect.

## Current lifecycle

Successful publication verifies the current record and marks the local sealed draft with its posted ID, retaining text and intent. It does not clear the editor cache. Background draft sync skips sealed records. The existing server transaction still retires the active cloud draft branch and fences late saves; this anti-resurrection mechanism is distinct from unloading the retained local cache. A late empty cloud tombstone is compatible with a confirmed retained post.

Every composer route/context has an explicit `prepareDraft` command. A route-keyed task waits for queued editor saves, then reads the account/origin-scoped journal. An unsealed draft opens unchanged without creating a network transport. A sealed draft is checked by its exact intent; author, body (or a deletion tombstone), visibility, audience and parent must match. A positive match retires that local cache into a blank draft with a fresh intent and a higher revision before enabling the editor. A missing/unreachable result preserves the same sealed draft for safe retry; a mismatched record is an error and never authorizes a clear. No body-text deduplication can erase an independently composed draft with the same words.

The editor is initialized only from the prepared command reply for the current account/scope/mode/route. Late openings and cloud replies cannot initialize another session. There is no cached `loadDraft` resource or per-keystroke resource refresh in this path. Context changes and direct `/write` reloads also prepare a session. Empty active editors show no posted text while preparation is pending. Replies and Public/Private drafts retain their separate scopes.

## Framework/operator learning

Match the mechanism to its lifetime: publication is a transaction, a resource is a potentially retained projection, and opening an editor is a command that must establish its own session. A refresh declaration is not a freshness barrier for copying a snapshot into state. The SDK already documents route-keyed tasks; this repair uses that contract rather than changing the SDK to disguise app behavior. A useful upstream investigation is whether tools can make retained/pending answers and snapshot initialization races easier for operators to inspect or diagnose. That is an ergonomic hypothesis, not an implemented framework patch. Removing redundant draft resource re-reads also shortens the authored storage path; no latency improvement has been benchmarked.
