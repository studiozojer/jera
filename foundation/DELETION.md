# Post deletion

The authenticated feed and thread ellipsis menu offers Delete only for the current author's active posts, including replies. Canonical daoUI Confirmation asks before deletion; Cancel preserves the post and route. Requests wait for server confirmation before changing the view. A failed or ambiguous request keeps the post visible, shows a retry message, and permits another attempt from the menu.

Snapback's `deletePost(id)` clears the body and sets a defaulted `deleted` flag. Its named table transition requires the existing author to equal the authenticated viewer and the next body to be empty/deleted; publication identity, audience, ancestry and time remain immutable. This also permits authors to delete their own private replies after losing audience read access, without returning hidden text. Other authors cannot delete a readable post or use a hidden ID to bypass authorization. Deleted roots leave the feed. Existing thread paths show “This post was deleted.” and retain other authors' replies; new direct replies to a deleted parent are refused. Those replies can still be independently deleted by their authors.

The author/intent tombstone prevents a delayed publication with the same intent from recreating the record. The client reads the current post after a successful publication receipt, because an engine receipt can precede deletion on another device. A confirmed deleted record settles the sealed draft and returns home instead of presenting an old successful receipt as a new post. This is application deletion; ordinary protected backups and historical engine receipts are not a secure-erasure facility.
