# Jera web deployment

The shared server’s deployment, backup, and restore procedures live in [jera-snapback](https://github.com/studiozojer/jera-snapback/tree/main/ops).

`web.caddy` serves compiled artifacts at `https://jera.ink`, redirects `www.jera.ink` to the root, and exposes a loopback-only check at port 4421. The auth unit allowlists `https://jera.ink/.exact/auth/callback` alongside the existing phone and local-live callbacks. The API stays at `https://snapback.jera.ink`; the web client uses the same verified DID and authoritative store as the phone. Public posts remain readable by signed-in Jera accounts; hosting the UI publicly does not change record permissions.

From a clean release checkout, run `node scripts/build-web-release.mjs <new-build-directory>` with Bun 1.4.2 on PATH. Then run `node scripts/package-web.mjs <build-directory> <new-public-directory>`. This verifies the build receipt, copies the OAuth callback and public assets, and adds the returning-browser storage migration before startup. Copy only this packaged public directory into `/opt/jera-web/releases/<full-source-sha>/`. Never serve the raw build directory, source checkout, credentials, fixtures, database or dependencies. Set directories to 0755 and files to 0644. Run `python3 <staged-repository>/ops/install-web.py <full-source-sha>` to atomically select it and install the Caddy import. The installer rolls back the web symlink and Caddy configuration if local checks fail. Releases remain on disk for rollback.

The extensionless OAuth callback is explicitly served as `text/html`. The fingerprinted Exact app bundle and stylesheet can be reused across visits. HTML, the upgrade bootstrap, manifests, callbacks and stable-name assets use `Cache-Control: no-store` so a new release is discovered immediately. No Caddy access log is enabled for the callback's one-time handoff parameters. Verify the sign-in page in a fresh browser, callback script execution, origin preflight and unauthorized record refusal. Real account consent and the authenticated posting journey remain distinct acceptance checks.

DNS cutover: replace Squarespace's root `@` A records with `91.98.204.141`, remove any root AAAA record unless it points to a verified address on this host, and point `www` at `jera.ink`. Preserve MX/TXT and all PDS, handle and Snapback records. Once DNS resolves here, Caddy obtains HTTPS certificates. Verify the public root, callback MIME type, API health and PDS health after propagation. The previous Squarespace root A values were `198.49.23.144`, `198.49.23.145`, `198.185.159.144`, `198.185.159.145`; restoring those redirects website traffic back but does not roll back backend writes.

The app's own `auth.callback https://jera.ink/.exact/auth/callback` grant is required as well as the server allowlist. Loopback previews admit their callback differently and cannot prove this production-origin boundary. Run `bun tests/hosted-signin.browser.mjs` from `` to exercise the root-domain page, production CORS/refusal, executable callback and real provider discovery/PAR without entering credentials. Before DNS cutover, `JERA_WEB_ARTIFACT_ORIGIN=http://127.0.0.1:<ssh-forward-port>` substitutes only root-domain asset transport with the deployed Caddy server. This is not proof of public DNS/TLS or completed user authorization.

## Internal iPhone releases through AppDrop

Prefer the local builder for Jera when the release Mac has enough disk space and compute available. Use the EAS AppDrop profile when local capacity is limited, another build is using the machine, or a cloud build is requested.

On each pull request, run `bun run test:app` and `npm test` and record the results in the PR. For an internal release, select the merged main commit, use its full checkout on the release Mac, and prepare the web package and iPhone build from that checkout. The Mac needs Jera’s pinned Bun and Exact SDK, the iPhone toolchain, and the project dependencies installed from the lockfile. The local publisher uses the existing AppDrop credential on this Mac. On another release machine, supply the management key through the release secret `APPDROP_MANAGE_KEY`. Keep that key and the private management link out of Git and build logs.

1. Run `bun run release:iphone prepare` to build a device IPA for on-phone signing. Its build number comes from the selected main commit’s first-parent count, so successive main releases advance it. The command saves the archive, source commit, build number and SHA-256 under `.local/appdrop/<commit>/`. Repeating this step checks the existing archive.
2. For changes that need a gateway update, deploy and check the gateway first. Activate and verify the web package using the procedure above.
3. Run `bun run release:iphone publish` in the same checkout. It checks the IPA hash and the live web manifest, updates the existing install link, and writes the confirmed revision to `published.json` alongside the archive. If publication was interrupted before confirmation, check the revision and build number on the AppDrop management page before retrying.
4. On the next device update, leave a draft saved while signed in. Open the existing link, install the update, reopen Jera and confirm the same DID and draft. Record the result with the release receipt. [Jera iPhone install](https://appdrop.app/d/vyau9rfizz)


The EAS `appdrop` profile builds an unsigned Exact device IPA on Xcode 27.1 for on-phone signing. Set `EXACT_BUILD_NUMBER` in that profile to the intended merged revision's first-parent count before submitting the release. Install the submission dependency in `app` with `bun install --frozen-lockfile`, then run `npx eas-cli@27.2.0 build --platform ios --profile appdrop` there. Check the resulting bundle ID and build number. The stable publisher above targets the existing release link.
